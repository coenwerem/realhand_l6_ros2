# realhand_hardware

`realhand_hardware` implements `realhand_hardware/RealHandSystem`, a `hardware_interface::SystemInterface` plugin for RealHand dexterous hands over Linux SocketCAN. One plugin instance controls one hand. The current implementation is physically validated on a right RealHand L6. Repository-level demos, installation instructions, and supported configurations are documented in the [top-level README](../README.md).

## Interfaces

The exported interfaces are defined by the `ros2_control` XML generated by the `realhand_l6_ros2_control` macro in `realhand_l6_description`.

| Interface | Kind | Meaning |
|---|---|---|
| `<joint>/position` | command | Target joint angle in radians, clamped to `[0, max_rad]` before CAN encoding |
| `<joint>/speed` | command, optional | Raw speed setpoint from 0 to 255; a `0x05` frame is sent when any joint speed command changes |
| `<joint>/torque` | command, optional | Raw torque setpoint from 0 to 255; a `0x02` frame is sent when any joint torque command changes |
| `<joint>/position` | state | Joint angle in radians; mimic-joint state is synthesized from the corresponding actuated joint |
| `<joint>/velocity` | state, optional | Zero-filled because the hand does not report joint velocity |
| `tactile_<finger>/force` | state, sensor | Sum of the finger's 12-by-6 taxel grid, ranging from 0 to 18360 |

The speed and torque command interfaces are initialized from `activation_speed` and `activation_torque` during activation so controllers always observe defined values. Joints that do not claim these interfaces retain the activation setpoints. Position, speed, and torque frames are transmitted only when their commanded values change, which avoids unnecessary CAN traffic while the hand is holding a command.

## Parameters

Parameters are set inside the `<hardware>` block of the `ros2_control` description. All parameters are optional.

| Parameter | Default | Meaning |
|---|---|---|
| `model` | `L6` | Hand model; selects the joint table, mimic ratios, taxel geometry, and CAN IDs |
| `can_interface` | `can0` | SocketCAN interface |
| `hand_side` | `right` | `right` or `left`; selects the default CAN ID (`0x27` right, `0x28` left) |
| `can_id` | side default | Explicit CAN ID in base-10 or `0x` hexadecimal notation |
| `joint_prefix` | `<hand_side>_` | Prefix removed from URDF joint and sensor names before model-table lookup; unprefixed names also work |
| `enable_tactile` | `true` | Enable tactile-matrix requests |
| `tactile_period_ms` | `50` | Period between tactile request bursts |
| `position_request_decimation` | `4` | Request joint position every N control cycles; position requests take priority over the tactile stream |
| `activation_speed` | `80` | Speed byte sent during hardware activation, from 0 to 255 |
| `activation_torque` | `200` | Torque byte sent during hardware activation, from 0 to 255 |
| `taxel_topic` | unset | Optional topic for publishing raw taxel grids as JSON from the receiver thread |

## Implementation Layout

The driver separates model data, protocol encoding, and ROS 2 hardware integration:

- `hand_model.hpp` contains model-specific joint names, radian scaling, mimic ratios, taxel geometry, matrix mode bytes, and CAN IDs.
- `protocol.hpp` implements the CAN frame codec independently of ROS 2.
- `realhand_system.hpp` implements the `ros2_control` hardware plugin.

The protocol codec and model table have bus-independent gtest coverage. End-to-end driver behavior is exercised against the L6 emulator in `realhand_l6_bringup` over a virtual CAN interface.

## Activation Sequence

On activation, the driver opens the SocketCAN interface and starts the receiver thread. It then reads the current joint position, commands that position back to the hand, applies the configured speed and torque limits, and initializes the exported state and command interfaces from the measured configuration. This sequence ensures that the first `write()` holds the current hand pose until an active controller sends a new command.
